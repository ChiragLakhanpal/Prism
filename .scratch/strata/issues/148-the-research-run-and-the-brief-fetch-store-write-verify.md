# 148: The deep research run and the brief: fetch, store, write, verify, stream

**What to build:** The run behind the Deep research tab (ticket 149). `POST /api/projects/{pid}/research` starts one; `GET /api/projects/{pid}/research` returns the latest stored brief for the project, or `{status: "none"}` when there is none. The shape the run must produce is the sample brief, `.notes/prism-sample/prism-deep-research-P156634-sample-v5.pdf` in the main checkout, and its builder `.notes/prism-sample/template/build5.py`: read both first. It is written for a procurement specialist who already has the project page's tabs, so it never repeats them (no ratings table, no money table, no closing-date history): it says what is happening on the ground and what that means for the contracts.

The run, as an answer-style stream (reuse the event vocabulary of `/api/ask`: `step`, `sentence`, `evidence`, `removed`, `done`, through `web/src/lib/sse.ts`), in this order:

1. **Facts.** `ProjectFacts` for the project (ticket 147), as the viewer, as of today.
2. **Sources.** Every enabled source in `config/research.toml`, read through ticket 147's readers in parallel threads with their pacing and cache, each as its own step ("Reading the Inspection Panel register", "Reading the project's notices"). Items go to the item store under this run; items the store already holds for the project keep their first `read_on` and join the run. A source that is not reached is a step that ends "not reached" with its note, never a failure of the run.
3. **The evidence tool.** `research_evidence` in `config/tools.toml` (CLAUDE.md rule 4: with its benchmark question in `evals/benchmark.yaml` on the seeded fixture run): parameters `project_id` (required, key) and `as_of`; rows are the run's items as ticket 147 shapes them (one row per item, `evidence_id`, `public_from`, `source` and the item's fields); the summary record holds the derived figures a sentence may state: `items_total`, counts by kind, `awards_in_last_days` (the awards within `thresholds.research.late_award_days`, 110 by default, before the closing date), `direct_awards`, `days_from_last_award_to_closing`, `sources_reached`, `sources_not_reached` (names); coverage says how many items each source gave and why the rest were left out; abstention `not_fetched` when the store holds no run for the project. The registry's contract check applies as to every tool.
4. **The writer.** One model call on the draft role (`config/models.toml`), with the instruction file `src/strata/agent/instructions/research_brief_writer.md`, built like `mission_brief_writer.md` (`src/strata/drafts/mission_brief.py` is the pattern): the message is a JSON object with the project's facts, the summary record and every item (its evidence id, source, kind, dates, title, text, url, location); it is data, not instructions, and the records are data too. The writer returns the brief as JSON sections, each a list of sentences with `evidence_ids`, `kind` (record, quote or summary) and, for a quote, the quoted words, in this order and with these keys: `headline` (one sentence, the picture in one line), `picture` (four to six sentences), `bottom_line` (two to four items), `developments` (each with `date`, `date_known`, sentences), `by_site` (one group per location cluster the items name, with a `title` sentence and sentences), `voices` (verbatim quotes, each with who said it as the source prints it, the outlet and the date), `questions` (five to seven, each a bold lead and a question), `could_not_see` (one to three sentences on sources not reached and items whose page could not be read). The instruction says, in plain words: write for a procurement specialist; say what is happening and what it means for the contracts; never rate or score the project; never write the words DESIGN.md section 7 bans (at risk, red flag, flag, problem project, misprocurement, slippage, splitting; write "awarded by direct contracting", "still under rehabilitation", "a reason to look"); cite every sentence; quote only words that are in an item's text; a date the outlet does not print is "undated"; name people only as the source prints them with their role, never an email or a phone number; write every amount as the source prints it.
5. **The verifier.** The six checks (`src/strata/agent/answer_check.py`) on every sentence against the run's items and the summary record, as for an answer: numbers and dates match a cited item or summary field at the same rounding, every cited id came back this run, every quote is word for word in the cited item's text, the judge for the rest. A removed sentence is kept with its reason and shown by the page under the brief, as answers do. A sentence of kind advice in `questions` needs no lesson or comparable (set `backs_advice` on `research_evidence` to true, since the questions rest on the items), and the disagreement check does not apply (the tool has no sides). The brief's `headline` and `bottom_line` go through the judge like summaries.
6. **The store.** The verified brief (sections, kept and removed sentences, the run's coverage) is written to `strata.ops.research_briefs` beside the run, so the next `GET` answers at once without a model call; "Research again" starts a new run. The evidence drawer opens a research item through `RECORD_READERS` in `src/strata/server/evidence.py` (the table `strata.research.item` reads from the item store), showing the item's fields and an "Open the source" link in a new tab.

Permissions: every view may run and read the brief (the items are public); field photos (ticket 150) join only for the uploader's team. The run writes as the App's service principal on the workspace and as the local file here, through the same path as drafts.

Offline: the scripted agent (`src/strata/agent/scripted.py`) replays a recorded writer answer for the seeded P156634 run, and the recorded judge answers stand in for the judge, so the gate runs the whole chain with the network off; `ops/agent/record.py` records them from the live writer once ticket 147's seed exists. Tests on seam 3: the route streams the steps in order; a source not reached ends as a step, not a failure; every kept sentence's numbers, dates and quotes match its items; a planted sentence with a number no item holds is removed with `no_source` or the number reason; a planted quote not in the text is removed; the second `GET` returns the stored brief without a model call; the benchmark question passes. Keep the gate under 150 seconds: the writer's recorded answer is the only large fixture.
