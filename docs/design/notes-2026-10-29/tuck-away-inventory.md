## Patterns to build once

So that each item below is a small change, not a new design:

1. **Made-by window** (new, for example `web/src/components/MadeBy.tsx`): a lucide `info` icon button, 24 px target, `ink-muted`, placed after the last word of the sentence it describes. Its accessible name says what it opens ("How I built this summary"). It opens a `DefinitionWindow` with `openOnHover`, holding the made-by sentence with its date as a `Num`. Items T1 to T4 use it.
2. **Count line only when rows are hidden.** `countLineOf` in `web/src/components/Table.tsx` returns nothing when every row shows and no filter applies. Paged lists, filtered lists (rule 42) and folded lists keep theirs, and so does `data-page-lead` focus after paging.
3. **Column definitions live in the head's window**, never as a second line under the head. Data readiness already has the windows; Following and the past range table get them.
4. **Abbreviations as Terms.** On chart labels and in foot strips, a Term window on "PAD", "ISR", "ICR", "PPAR", "PDO" counts as the spell-out (rules 10 and 22). This needs a DESIGN.md line.
5. **Feedforward as a button's description.** "The draft waits in Drafts for you to check. I send nothing." becomes the button's tooltip and its `aria-describedby`, so a screen reader still hears it.

## The bylines (ticket 111): which ones carry meaning

The verifier (`src/strata/agent/verifier.py`) never reads `data-byline`; it runs on the server. But one byline kind is the screen's counterpart to a verifier rule. Checks 2 and 4 let a sentence that cites nothing stand only when a tool abstained this turn, and judge it against that abstention.

| Where | Kinds | What decides the kind | Does the verifier depend on it? | Call |
|---|---|---|---|---|
| Answer panel, `components/Answer.tsx` (`InShort`, the answer's `h3`) | `inShort` over ready, unsupported and refused answers | The stream's status | No. The verifier's results show in the check line and the removed box | Drop the words. Keep `data-byline="inShort"` on a screen-reader-only `h3`, so heading navigation still lands on the answer |
| Answer panel, the same block | `heldBack` over an abstained answer (`data-answer="abstained"`) | A tool's abstention code (`config/tools.toml`, abstentions) that the stream reports | **Yes.** The held-back sentence can stand with no citation marker (the gallery's abstention sample, "I'm not giving a range from only 12 comparable packages. Here are all 12.", has none) only because checks 2 and 4 allow an uncited summary when a tool abstained this turn. The byline is the screen's sign of that state | Drop the words: the sentence is already first person (rule 16), the check line under it reports the checks ("Checked: 12 of 12 numbers match records."), and the rows follow. Keep `data-byline="heldBack"` on the screen-reader-only `h3`, with "Strata held back" as its screen-reader text |
| Plan check, `components/PlanCheck.tsx` | `found`; `heldBack` when the result is withheld | `found`: the fixed checks, with no model. `heldBack`: the public view's rule on active projects (rule 45, the roles file's views) | No. The plan check runs no model and no verifier | Drop the words. Keep `data-byline` on the finding block |
| Package workspace, section 1, `components/PastRange.tsx` | `found`; `heldBack` when fewer than 20 comparables | `find_comparables`' abstention (rules 15 and 16) | No. The package page runs no model and no verifier | Drop the words. Keep `data-byline` on the finding block |

So the implementer keeps every `data-byline` attribute and drops every visible byline word. Only the answer panel's `heldBack` marks a verifier rule, and it is the one to keep exactly as it is in the DOM.
