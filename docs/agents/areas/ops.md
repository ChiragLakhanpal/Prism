# Area brief: ops

Tickets with `Area: ops` build the repo's machinery and the operations around it: the scaffold and the gate, credentials and the day-one tests, the Databricks bundle, deploys, the nightly job, the demo-ready command, budgets and caps.

Read: `docs/PLAN.md` sections 2, 10, 11, 12, 13, 14, 16 and 18, and "The shared workspace" in `docs/agents/build.md`.

- The gate (`.githooks/pre-commit`) runs the ground-truth SQL and the offline tests in under 150 seconds (the cap in `gates/steps.toml`; two minutes until October 26, 2026) with no network, includes `python3 .claude/hooks/test_guard.py`, and, when only Markdown files are staged, runs only the steps marked `always`: the secret scan, the tests that read Markdown (ticket 80) and the proposal's checks.
- One gate runs at a time on a computer. Before its clock starts, the gate holds a lock on `strata-gate.lock` in the temporary folder (`$TMPDIR`), or on the file `STRATA_GATE_LOCK` names, which the gate's own tests point under `tmp_path`. A second gate waits up to 20 minutes (`lock_wait_seconds` in `gates/steps.toml`) and then gives up, and its two-minute cap counts from the moment it holds the lock.
- The gate runs its steps in lanes, side by side. To add a step to a lane, give it `lane = "<name>"` in `gates/steps.toml` and put it among the steps that have lanes, below the steps it needs in that lane. A step with no lane runs alone, after every step above it. A new pytest step names the folders it tests, so each test folder runs in exactly one step. A test folder whose tests read the fixture database runs in the python lane, below the build, and is named in `FIXTURE_READERS` in `tests/test_gate.py`.
- The python lane's tests run on eight pytest-xdist workers, and the ops lane's on six. Both steps use `--dist worksteal`, so a worker that runs out of tests takes some from a busy one. Every Python test must be safe beside the others: it writes only under its own `tmp_path` or a throwaway repo, opens the fixture database read-only, never changes the working folder, sets an environment variable only through pytest's `monkeypatch`, and listens on port 0 (or, when it must name a port, on one below the system's range, as `free_port` in `tests/test_server_start.py` does). A test that cannot run beside the others gets `@pytest.mark.xdist_group("<name>")` with a comment that says why, and its step's `--dist worksteal` becomes `--dist loadgroup`, because work stealing ignores the mark; `tests/test_gate.py` checks this.
- When a lane gets slow again, run `uv run --frozen pytest --durations=15 <its folders>` to find the slowest tests; one slow test sets a floor that no number of workers can lower. Then try more workers (`--numprocesses`) and keep the number that gives the lower total gate time over three runs by hand, since the lanes share the processors. Or move a folder that does not read the fixture database to a new lane.
- The Playwright tests run in two lanes, web-1 and web-2. Each lane builds the app and the gallery into its own folder, which `STRATA_WEB_OUT` names and `web/out-dirs.ts` reads. Each then runs half of the tests against that build with `--shard=1/2` or `--shard=2/2`, on workers for a third of the processors each. Without the variable, the builds go to `web/dist` and `web/dist-gallery`. To find a slow spec, run a lane's npm command with `-- --reporter=json` and add up each file's durations. Every axe scan goes through `web/tests/axe.ts`, which costs about half of axe's default run, and `tests/test_gate.py` fails a spec that builds its own. A third lane needs its own folder and the shards renamed to `1/3`, `2/3` and `3/3`. `tests/test_gate.py` checks that each lane tests the folder it built and that the shards cover every test once.
- The processors limit the gate more than its layout does. This computer has 16 processors, 12 of them fast. A gate costs about 900 processor-seconds (October 25, 2026): about half of it in the Playwright tests, a quarter in the python lane and a tenth in the ops lane. So moving steps between lanes saves little, and other sessions' tests on the same computer lengthen every lane: with the load average near 30, the gate took 70 to 90 seconds. A lower total needs less work. For example, run one axe scan where two tests scan the same page, in the same state and at the same width, or make pages load less code.
- Everything deploys from code: the bundle, the app, the jobs, the Genie space, the AI Search index and the Foundry agent. One command takes a fresh workspace to the demo state.
- Work on the shared workspace runs one at a time and leaves fairshare's catalog, app and job untouched.
- Human-only steps (tokens, the Azure sign-in, model deployments, the pay-as-you-go switch, budgets, inviting an outside reviewer) go into a wizard the user runs in their own terminal: call the Skill tool with `mattpocock-skills:wizard`.
- The wizard and the day-one probes write their results in `docs/day-one-results.md` in the main checkout, and those results are committed on build/strata like any other change. The gate checks that each marked block in that file is either the template's text or a recorded result, so a test of the wizard or a probe starts from a fresh rendering (`dayone.ensure_document`), never from a copy of the committed file.
- Caps are configuration: tokens per minute on each deployment, the daily page cap in ingestion, at most two replicas for anything hosted.
