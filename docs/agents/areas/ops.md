# Area brief: ops

Tickets with `Area: ops` build the repo's machinery and the operations around it: the scaffold and the gate, credentials and the day-one tests, the Databricks bundle, deploys, the nightly job, the demo-ready command, budgets and caps.

Read: `docs/PLAN.md` sections 2, 10, 11, 12, 13, 14, 16 and 18, and "The shared workspace" in `docs/agents/build.md`.

- The gate (`.githooks/pre-commit`) runs the ground-truth SQL and the offline tests in under 150 seconds (the cap in `gates/steps.toml`; two minutes until October 26, 2026) with no network, includes `python3 .claude/hooks/test_guard.py`, and, when only Markdown files are staged, runs only the steps marked `always`: the secret scan, a few tests that read the Markdown the docs write (ticket 80) and the proposal's checks.
- One gate runs at a time on a computer. Before its clock starts, the gate holds a lock on `strata-gate.lock` in the temporary folder (`$TMPDIR`), or on the file `STRATA_GATE_LOCK` names, which the gate's own tests point under `tmp_path`. The gate that holds the lock writes its process id and the time into that file. A second gate says which process holds the lock, waits up to 20 minutes (`lock_wait_seconds` in `gates/steps.toml`) and then gives up, and its 150-second cap counts from the moment it holds the lock.
- The gate runs its steps in lanes, side by side. To add a step to a lane, give it `lane = "<name>"` in `gates/steps.toml` and put it among the steps that have lanes, below the steps it needs in that lane. A step with no lane runs alone, after every step above it. A new pytest step names the folders it tests, so each test folder runs in exactly one step. A test folder whose tests read the fixture database runs in the python-1 and python-2 lanes' pytest steps, below each lane's build, and is named in `FIXTURE_READERS` in `tests/test_gate.py`.
- Since ticket 119 the Python tests that may read the fixture database run in two lanes, python-1 and python-2. Each starts with the fixture build, which keeps `data/out/fixture.duckdb` when nothing its last build read has changed (`gates/fixture_cache.py`, key in `data/out/fixture.inputs.json`; delete the key to force a build), and the two builds take turns on a lock. `--shard=1/2` and `--shard=2/2` (the root `conftest.py`) sort the test files by path and run the first or second half, so the split is the same everywhere. Starting each shard's slowest tests first, one per worker, was tried on October 28, 2026: it cost about 15% more processor time, because a moved test sets up its module's fixtures again on another worker, and saved no time, so the tests keep pytest's order. Both test steps set `STRATA_DUCKDB_THREADS=1` (read in `src/strata/lakehouse/engine.py`), so each worker's DuckDB runs on one thread: with DuckDB's default of one thread per processor in every worker, the second half took 96 seconds at a load of 25 against 36 on one thread.
- Each python lane's tests run on eight pytest-xdist workers, and the ops lane's on six. All three steps use `--dist worksteal`, so a worker that runs out of tests takes some from a busy one. Every Python test must be safe beside the others: it writes only under its own `tmp_path` or a throwaway repo, opens the fixture database read-only, never changes the working folder, sets an environment variable only through pytest's `monkeypatch`, and listens on port 0 (or, when it must name a port, on one below the system's range, as `free_port` in `tests/test_server_start.py` does). A test that cannot run beside the others gets `@pytest.mark.xdist_group("<name>")` with a comment that says why, and its step's `--dist worksteal` becomes `--dist loadgroup`, because work stealing ignores the mark; `tests/test_gate.py` checks this.
- When a lane gets slow again, run `uv run --frozen pytest --durations=15 <its folders>`, with the lane's `--shard=1/2` or `--shard=2/2` for a python lane, to find the slowest tests; the lane can never take less time than its slowest test, however many workers it has. Then try more workers (`--numprocesses`) and keep the number that gives the lower total gate time over three runs by hand, since the lanes share the processors. Or move a folder that does not read the fixture database to a new lane.
- The Playwright tests run in two lanes, web-1 and web-2. Each lane builds the app and the gallery into its own folder, which `STRATA_WEB_OUT` names and `web/out-dirs.ts` reads. Each then runs half of the tests against that build with `--shard=1/2` or `--shard=2/2`, on workers for a third of the processors each. Without the variable, the builds go to `web/dist` and `web/dist-gallery`. To find a slow spec, run a lane's npm command with `-- --reporter=json` and add up each file's durations. Every axe scan goes through `web/tests/axe.ts`, which costs about half of axe's default run, and `tests/test_gate.py` fails a spec that builds its own. A third lane needs its own folder and the shards renamed to `1/3`, `2/3` and `3/3`. `tests/test_gate.py` checks that each lane tests the folder it built and that the shards cover every test once.
- A screen test waits for an element or a state, never for a fixed time: `expect` and `expect.poll` for what the page shows, `fontsLoaded` in `web/tests/settled.ts` before it measures where text lands, and the page's own clock (`page.clock`) when the page counts time itself, as the range chart's 100 ms rest does; a fixed wait is only ever the window in which a test checks that nothing happens. A timing assertion reads the clock nearest what it checks, such as the time the gate prints for itself, and keeps at least a second spare over what it takes alone, because the gate runs beside other builds at load averages of 20 to 40 (ticket 56).
- The processors limit the gate more than its layout does. This computer has 16 processors, 12 of them fast. A gate cost about 900 processor-seconds on October 25, 2026: about half of it in the Playwright tests, a quarter in the python lane and a tenth in the ops lane. On October 28, 2026, it cost about 1,700 (measured with `/usr/bin/time` around `.githooks/pre-commit`), about 500 of them in the two python lanes' tests, so it cannot end much under two minutes on 16 processors. So moving steps between lanes saves little, and other sessions' tests on the same computer lengthen every lane. A lower total needs less work. For example, run one axe scan where two tests scan the same page, in the same state and at the same width, or make pages load less code.
- Everything deploys from code: the bundle, the app, the jobs, the Genie space, the AI Search index and the Foundry agent. One command takes a fresh workspace to the demo state.
- Work on the shared workspace runs one at a time and leaves fairshare's catalog, app and job untouched.
- Human-only steps (tokens, the Azure sign-in, model deployments, the pay-as-you-go switch, budgets, inviting an outside reviewer) go into a wizard the user runs in their own terminal: call the Skill tool with `mattpocock-skills:wizard`.
- The wizard and the day-one probes write their results in `docs/day-one-results.md` in the main checkout, and those results are committed on build/strata like any other change. The committed file may already hold results, so a test of the wizard or a probe starts from a fresh rendering (`dayone.ensure_document`), never from a copy of that file, and the gate checks that each marked block is the template's text or a recorded result.
- Caps are configuration: tokens per minute on each deployment, the daily page cap in ingestion, at most two replicas for anything hosted.
